Lab 2 - Using GDB
Observed on 21/10/2026, branch lab2-gdb, base commit 99161db.

Q1. Which function called syscall()?
usertrap() called syscall(). The backtrace shows syscall() in frame #0
and usertrap() at kernel/trap.c:68 in frame #1.

Q2. What is p->trapframe->a7 and what does it represent?
Its value is 0xf (15), which is SYS_open in kernel/syscall.h.
The saved a7 register contains the system call number requested by the
user process. Here the process is init. In this source version, init
starts by calling open("console", O_RDWR) in user/init.c.
This source version does not contain user/initcode.S; its startup code
loads /init with kexec() in forkret() in kernel/proc.c.

Q3. What was the previous CPU mode?
The previous mode was User mode. GDB reports sstatus = 0x200000022.
The SPP field (bit 8) is 0, as verified by (($sstatus >> 8) & 1).
SPP records the privilege mode before the trap; it is not the current
mode. At the breakpoint the processor is executing kernel code in
Supervisor mode.

Q4. Which instruction causes the panic, and which register corresponds
to num?
For the temporary experiment num = *(int *)0, the observed panic sepc
is 0x80001d62. kernel/kernel.asm and GDB show:
  0x80001d62 <syscall+16>: lw a3,0(zero)
This instruction attempts to load a 32-bit value from virtual address 0
into a3. Thus a3 is the destination register corresponding to num for
this compiled statement. The load faults, so the assignment does not
complete. Addresses and register allocation depend on the build.

Q5. Why does the kernel crash?
The temporary statement dereferences a null pointer. Virtual address 0
has no valid mapping in the kernel page table; this is not equivalent
to assigning the integer 0 to num.
The observed trap values are:
  scause = 0xd (13, load page fault)
  sepc   = 0x80001d62 (the faulting instruction)
  stval  = 0x0 (the faulting virtual address)
GDB also shows the next-level page-table entry for virtual address 0
is zero (invalid), although the root entry exists for other low-address
mappings. kerneltrap() treats this unhandled kernel fault as a panic.

Q6. Which process was running when the kernel panicked?
At the breakpoint on the faulting instruction, p->name is "init" and
p->pid is 1. The saved syscall number is 0xf (SYS_open).

After the experiment, num = p->trapframe->a7; was restored. The source
was verified byte-for-byte against its pre-experiment SHA256, and the
kernel was rebuilt. Screenshots and logs are stored separately under
Project2/minh-chung/T02-GDB on the Windows filesystem.
